# Zone Event Schema

Status: Phase 1 architecture contract  
Scope: MySnoozePod showroom sensor and IoT layer  
Runtime code: not implemented in this pass

## Purpose

`ZoneEvent` is the canonical normalized event contract for the showroom sensor layer.
It sits between raw sensor/controller input and customer-facing showroom experiences.

Required pipeline:

```text
Sensor
-> production edge controller
-> AWS IoT Core using MQTT over TLS
-> IoT Rule
-> Lambda using Node.js 20
-> DynamoDB latest zone state
-> DynamoDB append-only event history
-> API Gateway WebSocket push
-> React showroom and operator surfaces
```

No polling is part of this contract.

## Event Classes

| Class | Producer | Example | Meaning |
| --- | --- | --- | --- |
| Raw sensor signal | Physical sensor or edge firmware | pressure pad active, mmWave target present | Hardware observation before business rules. |
| Normalized zone event | Edge controller or ingestion Lambda | `pod_occupied`, `presence_detected` | Canonical event accepted by cloud ingestion. |
| Derived experience event | Backend rules after validation/session checks | `rest_test_start_eligible` | Experience-level signal. Sensors must not decide this alone. |

Example distinction:

| Event | Class | Notes |
| --- | --- | --- |
| `pod_occupied` | Normalized zone event | A Pod occupancy sensor reports occupied state. |
| `rest_test_start_eligible` | Derived experience event | Backend confirms pod, session, and current state make Rest Test start appropriate. |

The sensor must not independently decide that a Rest Test has started.

## Event Type Rules

| Event Type | Normal Producer | Expected State | Notes |
| --- | --- | --- | --- |
| `presence_detected` | Edge controller | `active` | Proximity only; does not imply occupancy. |
| `presence_cleared` | Edge controller | `inactive` | Clears proximity context. |
| `pod_occupied` | Pod edge controller | `active` | Pod zones only. |
| `pod_vacated` | Pod edge controller | `inactive` | Pod zones only. |
| `rest_test_start_eligible` | Backend/system | `active` | Derived after session/state checks. |
| `rest_test_pause_eligible` | Backend/system | `warning` or `active` | Derived from vacancy, timer, or manual logic. |
| `rest_test_end_eligible` | Backend/system | `warning` or `active` | Derived from vacancy, timer, or manual logic. |
| `help_requested` | Frontend or staff | `active` | Human assistance path only. |
| `lighting_state_changed` | Edge controller or system | `active` or `inactive` | Reflects light zone state. |
| `manual_override` | Staff or system | `active` | Must include override reason in metadata. |
| `device_heartbeat` | Edge controller | `active` | Device liveness. |
| `device_fault` | Edge controller | `warning` or `error` | Fault details must be in metadata. |

## Timestamp Rules

- `timestamp` must be ISO-8601 UTC, for example `2026-07-16T12:30:45.123Z`.
- Edge devices should use synchronized time.
- Ingestion Lambda must add `receivedAt` separately; it must not overwrite `timestamp`.
- Events more than five minutes in the future are rejected.
- Events older than the zone's stale window are written to event history but cannot update latest state unless manually replayed by an operator process.

## Sequence Rules

- `sequence` is monotonic per `deviceId`.
- Sequence starts at 1 after controller boot.
- Controller reboot may reset the sequence only if `metadata.bootId` changes.
- Latest-state updates must reject older sequence values for the same `deviceId` and zone.
- Event history remains append-only even when a sequence is old.

## Confidence Rules

- `confidence` is 0.0 through 1.0.
- Use null when a sensor does not provide confidence.
- Suggested thresholds:
  - `>= 0.80`: normal automated handling.
  - `0.50-0.79`: accept but mark lower confidence for operator diagnostics.
  - `< 0.50`: write to history but do not produce customer-facing derived events unless confirmed by another signal.

## Malformed Event Handling

Malformed events must not reach customer-facing React/HUD paths.

Handling:

1. Reject invalid JSON.
2. Reject missing required fields.
3. Reject invalid enum values.
4. Reject topic/payload environment mismatch.
5. Reject unregistered device IDs.
6. Reject unregistered zone IDs.
7. Reject disabled devices.
8. Quarantine malformed payloads with reason codes.
9. Emit CloudWatch metric `ZoneEventMalformed`.
10. Do not update latest state.
11. Do not broadcast over WebSocket.

## Duplicate Event Handling and Idempotency

- `eventId` is the primary idempotency key.
- Event history writes must use a conditional expression so the same `eventId` is not appended twice.
- Duplicate valid events should return success from Lambda but emit metric `ZoneEventDuplicateSuppressed`.
- Duplicate events must not repeat WebSocket broadcasts, profile mutations, lighting commands, or Snoozer speech.

## Stale Event Handling

An event is stale when:

- Its `timestamp` is older than the latest accepted device timestamp for the same zone and device.
- Its sequence is lower than the latest accepted sequence for that zone/device.
- Its timestamp is beyond the configured stale window.

Stale events:

- May be appended to event history with `stale: true`.
- Must not overwrite latest state.
- Must not trigger derived experience events.
- Must not trigger customer-facing HUD output.

## Environment Mismatch Rejection

The topic environment and payload `env` must match.

Examples:

- Topic `mysnoozepod/prod/...` with payload `"env": "dev"`: reject.
- Topic `mysnoozepod/dev/...` with payload `"env": "prod"`: reject.

Dev and prod must remain isolated.

## Registered Device and Zone Validation

The ingestion Lambda must validate:

- `deviceId` exists in the IoT registry for the same env and store.
- Device is enabled.
- `zoneId` belongs to the device or controller.
- `sensorId` belongs to the registered device.
- `sensorType` matches the registered sensor definition.
- Pod zones include matching `podId`.

Unknown or disabled devices fail closed.

## Anonymous vs Identified Session Behavior

- Sensor events are anonymous by default.
- `sessionId` may be attached only after deterministic session association exists.
- `snoozeCode` must remain null until deterministic Snooze Code/session association exists.
- Presence alone must not attach Snooze Code.
- Checkout/cart state must never be inferred from sensor events.

## Privacy Boundary

The MVP sensor layer records zone state, not biometric identity.

Do not include:

- Face recognition data.
- Biometric data.
- Medical claims or health diagnoses.
- Raw audio transcripts.
- Payment details.
- Shopify cart contents unless already present through approved cart/session APIs.
